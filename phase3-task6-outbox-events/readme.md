# Growth Instrumentation & Transactional Outbox Engine 

This module implements the **Growth Instrumentation & Transactional Outbox Engine** for the PlaceMux backend. It provides a reliable **Transactional Outbox Pattern** to guarantee ordered, durable, and idempotent event delivery for analytics and downstream systems.

The engine ensures that business events generated by the application are never lost, even in the event of failures, while supporting event replay for rebuilding downstream projections and analytics.

# Core Architecture & Workflow

## 1. Transactional Outbox

Business events are first written into a durable **Transactional Outbox** before being dispatched to downstream consumers.

Each event contains:

- Event Type
- Schema Version
- Tenant ID
- Payload
- Sequence Number
- Processing Status
- Timestamp

This guarantees that no event is lost during failures.


## 2. Ordered Event Processing

Every emitted event receives a monotonically increasing:

```text
sequence_number
```

This ensures:

- Strict event ordering
- Deterministic processing
- Consistent replay
- Reliable downstream synchronization


## 3. Event Replay

Historical events can be replayed starting from any sequence number.

Replay functionality supports:

- Analytics rebuilding
- Recovery after failures
- Consumer synchronization
- Event sourcing scenarios

# Evaluator Validation Guide

Configure the required environment variables.

```bash
export BASE=http://localhost:3009/api/v1
export TENANT_UUID="a1b23c44-dd55-66ee-77ff-88aa99bb0011"
```


## Step 1 — Emit a Business Event

```bash
curl -X POST "$BASE/growth/events/emit" \
  -H "Content-Type: application/json" \
  -d '{
    "event_type": "APPLICATION_SUBMITTED",
    "schema_version": "v1.0",
    "tenant_id": "$TENANT_UUID",
    "payload": {
      "application_id": "8a329d41-cc21-4112-9114-1da21e48bc01",
      "candidate_id": "4b111d42-ab12-4211-8224-2da21e48bc02"
    },
    "idempotency_key": "outbox-emit-token-001"
  }'
```

### Expected Result

Returns **HTTP 201 Created**.

Example response:

```json
{
  "success": true,
  "status": "pending",
  "sequence_number": 1
}
```

Verify that the event has been stored in the **Transactional Outbox** with a `pending` status and a strictly increasing sequence number.


## Step 2 — Process Pending Events

```bash
curl -X POST "$BASE/growth/outbox/process"
```

### Expected Result

Returns **HTTP 200 OK**.

Example response:

```json
{
  "success": true,
  "events_processed": 1
}
```

Pending events are dispatched to the analytics event store in sequence order and marked as `processed`.


## Step 3 — Replay Historical Events

```bash
curl -X GET "$BASE/growth/events/replay?from_sequence_number=1"
```

### Expected Result

Returns **HTTP 200 OK**.

Example response:

```json
{
  "success": true,
  "events": [
    {
      "sequence_number": 1,
      "event_type": "APPLICATION_SUBMITTED"
    }
  ]
}
```

The response demonstrates that historical events can be replayed from any sequence number to rebuild downstream consumers.

# Event Emission Workflow

```text
Business Event
       │
       ▼
Validate Request
       │
       ▼
Persist to Outbox
       │
       ▼
Assign Sequence Number
       │
       ▼
Mark Pending
       │
       ▼
Return Success
```


# Event Processing Workflow

```text
Pending Events
       │
       ▼
Read Outbox
       │
       ▼
Sort by Sequence Number
       │
       ▼
Dispatch to Analytics
       │
       ▼
Mark Processed
       │
       ▼
Persist Processing Status
```


# Event Replay Workflow

```text
Replay Request
       │
       ▼
Read Starting Sequence
       │
       ▼
Fetch Historical Events
       │
       ▼
Return Ordered Stream
```
